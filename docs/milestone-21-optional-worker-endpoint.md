# M21 authenticated default-off optional worker endpoint

This adds POST /api/internal/optional-email/run and composes the accepted worker, queue, fresh dispatch-state store, unsubscribe-token issuer, Resend transport and durable provider receipt store. It does not add/change SQL, job creation, campaign content, schedules, webhooks or existing delivery modules. Seven repository additions only: handler, composition, route, three tests and this document. Publishing does not activate sending.

The Node route has maxDuration=60 and accepts one machine-only POST with no body, content type, transfer encoding, Origin, query or fragment. Optional Content-Length must be exactly 0. Cookies, user sessions, job IDs, recipients, payloads, enable overrides and query tokens are never accepted as authorization/input. GET/other methods cannot execute. A dedicated exact 64-lowercase-hex bearer secret is compared using constant-time equal-length bytes; missing/malformed configuration fails closed. Raw errors, secrets, bearer URLs, recipients, job IDs and provider IDs are never returned/logged by the new code. Responses contain only status/processed and no-store headers; there is no CORS opt-in.

Server-only configuration (never NEXT_PUBLIC): PIPSTART_OPTIONAL_WORKER_SECRET is the dedicated machine bearer; PIPSTART_OPTIONAL_WORKER_ENABLED must be exactly the lowercase string true; PIPSTART_OPTIONAL_RESEND_API_KEY is the dedicated optional-delivery Resend key. Whitespace/newlines are rejected, not silently trimmed. Missing flag is OFF. There is no fallback to account-monitor, webhook, sweep, user or alert credentials. The runtime composition independently defaults to disabled and requires explicit true plus a valid provider key before creating stores. All endpoint checks precede the lazy composition callback and persistent admission. Do not configure/enable these values as part of patch application or publishing; separate authorization is required.

One request invokes exactly one accepted fixed worker batch: at most five existing due pending jobs, sequentially, no refill, recursive polling or automatic retry. The persistent singleton gates concurrent requests; the approved database cadence/reservation caps remain authoritative, including the platform 50-reservations/24h limit and recipient/category windows. This is not an IP-based HTTP/DDoS rate limiter: deployment/platform protections remain necessary. Unauthorized requests do no SDK/RPC/provider work. A stolen machine credential plus an already enabled deployment can trigger bounded existing queued work; it does not authorize arbitrary request content or bypass database cadence, but it must still be treated as sensitive operator authority.

The real accepted queue path is retained: claim, fresh preferences/account/address checks, category+all unsubscribe tokens/footers, durable SENDING and cadence reservation, last eligibility check, immediate non-retried Resend handoff with stable job idempotency and correlation tags, durable provider acknowledgement, then queue checkpoint. Current address blocks, opt-outs and frequency remain enforced in the existing SQL dispatch state. No accepted/unresolved job is selected for automatic replay. Unknown handoff, lost receipt/checkpoint, malformed admission/result or exception returns review_required and retains conservative worker admission. No finally unlock or recovery RPC is called. Cadence denial currently maps to lease_lost and therefore also conservatively retains admission for owner review; this patch does not silently change that accepted behavior.

HTTP 200 means empty or completed batch processing, not Gmail arrival or signed delivery evidence. processed counts attempted worker jobs, including suppressions, not delivered emails. busy returns 409 without processing. disabled, not_configured, unavailable and review_required use 503; unauthorized uses 401; invalid input 400. Do not configure automatic HTTP retries, even for timeout/503: a response may be lost after some jobs were accepted. Inspect persistent worker/job/provider evidence and use the separately approved owner recovery process only after stopped-executor proof. Provider/API and signed callbacks remain separate facts; no provider response is represented as inbox delivery.

This endpoint has a 60-second deployment budget but no guarantee that five provider requests plus database round trips finish within it. A platform timeout/disconnect can leave the singleton/job in review. Never infer a stopped remote executor merely from an HTTP error or idle local shell. No scheduler or heartbeat is attached to this optional worker. The existing account-email watchdog is unrelated and unchanged.

The enable flag is deployment-scoped, not a global database kill switch. Disabling it and redeploying rejects new work at that deployment but cannot recall in-flight sends or disable an older deployment URL retaining enabled configuration. Before any future activation, inventory/protect or retire other enabled deployments and design/test the operator stop procedure; provider-key revocation and database controls have different scopes. This batch deliberately stays OFF and does not claim that setting an env flag fences old executors.

Next gates: apply/verify these files, explicitly authorize commit/push, confirm production default-off behavior without sends, then finish trusted job creation/approved content and activation/stop controls before any separately authorized controlled worker send. No customer campaign, automatic activation, provider-key creation, secret copy, worker unlock, production send or environment change is authorized by this patch. No migration gate is needed for these seven source additions because the accepted database functions are reused unchanged.

Tests cover strict bearer/config/default-off/input rejection with zero runtime calls, sanitized aggregate responses, lazy route wiring without fallback, and the real worker/queue/dispatch/transport stack using fake stores and mocked fetch. They prove unsubscribe headers/tags/idempotency/checkpoint order, final opt-out suppression, missing dependencies, busy admission, cadence denial, uncertain provider/receipt/checkpoint retention and a five-job sequential batch. Existing optional-email/unsubscribe unit regressions and a production no-emit TypeScript overlay also run. Tests use only generated in-memory fixtures; there is no real network request or database operation.
