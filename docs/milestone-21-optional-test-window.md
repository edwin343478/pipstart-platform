# M21 database-backed one-job test window

This is a default-closed acceptance control, not general campaign activation. Three additive files: one migration, generated SQL assertions and this document. No existing RPC body, signature, application route, environment variable, scheduler, provider configuration or grant is replaced.

Two private RLS tables store the current singleton permit and append-only-by-convention revision audit. Public, anon, authenticated and service_role receive no table or new-function grants. The database owner can pause with `pipstart_set_optional_test_window(null,null,<opaque M21 proof reference>)`; arming instead needs exactly one existing due pending job and a future expiry no more than 15 minutes away. Arming refuses active admission and preparing/sending/manual jobs. This tool does not create a job, approve its content or recipient, enable a deployment, supply a key or execute a worker. Proof references identify an external operator decision; they are not cryptographic proof or credentials.

Existing admission RPCs in older deployments encounter a trigger requiring their complete selected batch to equal the single permitted job. An unrelated/mixed batch raises before admission commits; it is never filtered into an implicit new audience. A second trigger guards every transition into SENDING, including a direct queue path without worker admission. It atomically consumes the permit with that transition. Failed transitions roll back the cadence reservation/content facts and consumption audit. Expired/missing permits fail closed. Newly installed tables are closed; installing the migration does not activate sending or touch existing job content.

The owner pause serializes on the permit row with admission/handoff transactions. Once pause commits, new admissions or SENDING transitions cannot pass the closed permit, regardless of an old deployment's environment flag. Existing old application code may report review_required / lease_lost or a sanitized database error; no new API result schema is asserted. A closed gate never clears admission, changes job status or refunds budgets. Apply the accepted recovery protocol only after stopped-executor proof. Database locks are transactional, not provider-call locks.

Critical limitation: a committed SENDING transition is already admitted in-flight work even if the external provider call has not started. Pause cannot recall it; its existing executor may still make that one handoff after pause returns. Expiry also prevents only new boundary crossings, not a handoff already admitted. Never claim a zero-in-flight global kill switch. Before a controlled test, isolate the dedicated optional provider credential/deployment, inventory older endpoints/executors, approve exact content/recipient/job, review all other pending and unresolved work, and record how to stop/fence the provider-facing executor. Do not revoke shared account-email credentials. Privileged database owners can bypass triggers; this is an application/service-role boundary, not protection against the database owner.

Migration installation requires idle worker admission and no preparing/SENDING rows, uses a five-second lock timeout and makes no automatic repair. It adds guards without replacing existing cadence, recovery, receipt, hold or content logic. Trigger ordering does not substitute for the existing send-time preference/suppression checks. No secret is stored in the permit/audit. Audit includes job UUID, proof reference, database session, revision and timestamp; restrict owner access and decide its retention/export policy before live use. No automatic audit pruning is added.

Validation uses a generated temporary database only: closed/expired/wrong/mixed-job paths, original RPC admission and handoff, zero reservation on rejection, pause after admission, one consumed permit, retained uncertain admission, privileges and a two-connection pause-before-handoff ordering test. Baseline worker/cadence tests run before this new default-closed control, followed by gate-specific integration tests. A successful local test is not a hosted migration, provider send, live stop drill or final M21 signoff.

Rollout: pass isolated tests; explicitly authorize local/hosted application migration and hosted read-only acceptance; apply only these three reviewed additions; explicitly authorize commit/push and verify deployment; then use a separately approved one-job live-worker test plan. Keep the permit closed throughout rollout. Do not auto-rollback the migration or drop guards as a retry shortcut.
