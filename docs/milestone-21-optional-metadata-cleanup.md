# M21 bounded manual metadata cleanup (dormant)

Scope is only cadence reservations strictly older than 31 elapsed days (744 hours) and controlled-recovery audits strictly older than 365 elapsed days (8760 hours). At most 100 records TOTAL across both tables may be removed in one invocation, ordered oldest first then kind/reference. This does not minimize message content or delete jobs, provider receipts/events, unsubscribe tokens, preferences, suppression/import records, investigation holds or worker admission. The 90-day content-minimization compatibility work remains outstanding.

Three functions and a private receipt table are owner-only, with no anon/authenticated/service_role grants, no SECURITY DEFINER elevation and empty search paths/UTC normalization. There is no route, schedule, worker call site or live-delete command. Installing the migration does not execute cleanup. The earlier retention inventory remains a non-destructive policy report; its disabled flags are not a claim that this separately installed manual owner capability does not exist. Automatic cleanup and payload cleanup remain disabled.

The private candidate helper centralizes the approved hold/unresolved rules: direct job holds, recovery holds and linked jobs, active-batch membership, and extant nonterminal jobs are excluded. Orphans beyond the full window can be reviewed, but held orphan IDs remain protected. Recovery holds cannot disappear through deletion of their audit because held audits are excluded. Current 30-day/7-day/24-hour budgets are not shortened by removing records beyond 31 days.

The plan returns only a fixed evaluation timestamp, SHA-256 plan hash, aggregate selected counts, maximum 100 and disabled automatic/payload/resend flags. Its hash binds policy durations, evaluation time and the exact bounded candidate IDs/digests, including each full metadata row and relevant job status/update checkpoints. Private helper row references must not be printed publicly. The plan is not permission to delete: before any real execution an operator must review the applicable preview, record investigation holds, retain an approved recoverable backup/export for the exact batch and obtain explicit authorization for that batch.

Execution requires the exact plan timestamp/hash, an opaque `M21-` proof reference and an explicit assertion that optional senders/producers/schedules are stopped and cannot resume. That assertion is human-supplied, not technical fencing. The plan may be no older than 15 minutes and cannot be future-dated. A missing/busy admission or contended five-second lock fails closed. The singleton is locked without changing it, and table writers are blocked briefly so holds/job eligibility/candidate rows cannot drift across comparison and deletion. An unexpected hash returns `changed`; never automatically refresh-and-delete after rejection.

Targets are frozen once under the locks, so deleting one class cannot refill the other class and exceed 100. Deleted counts must match the reviewed plan. The atomic receipt contains an opaque UUID, unique plan hash, plan/effect times, proof reference, database session role and deleted counts; no row list, recipient, body, raw token or secret is recorded. The role is not a verified human identity: private proof records must identify the reviewer. Receipt insertion failure rolls all deletion back. An exact replay of a recently executed plan returns `already_recorded`, never another batch. No-work returns without deletion or a success receipt. A stale/uncertain outcome requires read-only receipt inspection, not blind retries or draining a backlog.

Receipt rows have no cascading parent FK and are not automatically pruned in this batch. Their long-term retention/access decision must be included in the operator review before first real cleanup; the approved 365-day rule covers recovery audits, not an silently assumed rule for these new execution receipts. A privileged owner can alter data directly, so this is not tamper-proof auditing. Deletion is not intrinsically recoverable from the receipt: actual first deletion requires a separately authorized protected backup/export and restore plan, never an in-chat dump of private metadata.

Generated tests cover API-role denial, fixed 100 total cap, recent/held/unresolved protection, new-hold and row drift, sender-stop attestation, stale/future plans, UTC stability, active admission, audit rollback, repeat acknowledgement and unchanged job/token/evidence/preference/hold/admission data. A two-connection test verifies serialized execution and one receipt for the same plan. Focused preparation only creates/removes generated test databases; no application/hosted migration or real cleanup runs. Real execution, further content minimization, full release regression and sending activation remain separately authorized gates.
