# M21 owner-only controlled worker recovery (dormant)

This adds a private audit table and two database-owner-only functions. Neither anon, authenticated nor service_role receives table access or function execution. There is no route, scheduler, worker call site, browser control, reset button, enable flag or real-run recovery script. Deployment does not unlock a worker or send email.

Recovery requires the exact run fingerprint, a fresh private-state snapshot hash, explicit boolean executor-stopped attestation and an opaque `M21-` proof reference (8–80 following ASCII letters/digits/underscore/hyphen). The reference must map to privately retained evidence and the human authorization for this specific run. Never put credentials, unsubscribe URLs, email content or personal descriptions into that reference. `database_session` identifies the database connection role, not an authenticated human; the external evidence must identify the actual reviewer.

The attestation is a human assertion, not technical proof supplied by PostgreSQL. Before making it, stop/fence every executor for the selected run and prove it cannot resume a provider call. Age, a timeout, deployment, no callback or an absent acknowledgement does not establish this. If that proof is missing, do not invoke recovery. Current optional callers/producers/schedules must remain disabled. A separately authorized case-specific operator command is required for a real blocked run; this patch intentionally supplies none.

The read-only snapshot helper returns only status, run fingerprint, SHA-256 snapshot hash, selected-job count and `resendAllowed:false`. Its UTC canonical hash covers the full singleton row, every existing selected job (including prepared payload and lease state), provider receipts, individual delivery events and cadence reservations. Missing selected jobs are represented by the slot's unchanged ID list and absence from row arrays. It exposes no raw run token, recipient, body, provider identifier, bearer link or job content. The hash is sensitive operational metadata, not proof of executor shutdown or anonymity. Snapshot/report details remain owner-controlled.

Recovery first locks admission, then briefly blocks queue/evidence/reservation writers, recomputes the snapshot and compares both exact hashes. The five-second lock timeout fails closed on contention. Any changed lease, job, individual provider event/receipt, reservation or slot causes `changed`; do not reuse a stale snapshot or automatically retry. UTC normalization prevents session timezone differences from inventing drift. The original read-only human review report must also be considered; this hash is a compare-and-set guard, not a replacement for job review.

On an exact match the function inserts one immutable-by-API recovery record and clears only the singleton admission in the same transaction. Audit failure rolls back the unlock. There is no generic reset API, no table/API grants and no cascading FK that would erase the audit when an account/job is deleted. The private record contains run/snapshot hashes, proof reference, database session role, original start/recovery times and selected job UUIDs, but no email content or raw run token. Retention/access policy for this audit remains required before campaign launch. A privileged database owner can still modify rows directly; this is not tamper-proof against that owner.

All job rows, leases, statuses, prepared payloads, provider evidence, due times, attempts, preference/suppression state and cadence budgets remain unchanged. In particular sending/manual jobs stay quarantined, and preparing jobs are not auto-selected by the worker. Missing jobs are not recreated. Future pending jobs may be selected only by separately enabled normal worker processing with fresh eligibility/cadence checks. Recovery never queues a replacement, changes a dedupe key, refunds capacity or authorizes resend. Every result keeps `resendAllowed:false`.

Two competing recovery attempts serialize: only one can audit/clear a given run; subsequent calls see idle, and a stale request cannot clear a different active run. An idle response is not permission to resume work. An uncertain recovery acknowledgement requires read-only inspection of admission and the matching private audit record, not message replay or blind mutation retries.

Generated isolated tests cover denied roles, missing/false attestation, bad proof references, stale job/evidence/reservation/slot snapshots, UTC stability, exact-match recovery, unchanged jobs/evidence/budgets, audit rollback, repeated/stale recovery and two-connection contention. No real-run recovery, provider email, application/hosted migration or activation occurs during preparation. Existing normal worker finish and read-only review are unchanged. Final release regression, retention, content/abuse controls and authorized activation remain separate.
