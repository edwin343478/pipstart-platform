# M21 dormant bounded worker

This batch adds a coordinator, service-only store, singleton admission migration and generated tests. There is no call site, route, environment switch, schedule, producer or provider activation. `runOptionalEmailWorker` is disabled unless explicitly passed boolean true with every dependency present. Security/reset/operator mail remains separate.

The database serializes admission using the singleton row lock, then stores an opaque run token and at most five due pending job IDs in deterministic due/created/UUID order. Two processes cannot acquire admission together. Only one fixed batch is returned; the coordinator processes it sequentially with the existing queue consumer and all its latest-state, suppression, cadence and durable-handoff checks. It does not refill the batch, manufacture replacement jobs or retry provider calls. Preparation attempts exhausted at five are excluded. Preparing/sending/manual jobs are never selected by this worker.

Admission does not expire and has no automatic takeover or generic reset RPC. A crashed/hung run, lost admission acknowledgement, malformed result, provider/manual/uncertain outcome or lost completion acknowledgement stops for review. The coordinator does not unlock in `finally`. Normal completion uses the exact run token; the database refuses completion if any selected extant job is preparing, sending or manual. Old tokens cannot finish a different run. Unselected rows remain untouched. A process killed after admission can leave pending work blocked indefinitely: this is deliberate fail-closed behavior, not high availability.

The current consumer's `lease_lost` includes both safe cadence deferrals and ambiguous lost leases. This worker conservatively stops and retains admission on either. Before campaign activation a reviewed operational recovery procedure must distinguish durable safe deferral from uncertain sends, confirm the old executor cannot resume, and handle the remaining batch. Do not manually clear the row or replay jobs to force progress. The run slot is coordination metadata, not a permanent audit ledger.

The RPCs are service-role only, SECURITY DEFINER with empty search_path; the singleton table has RLS and no direct API grants. This is a coordinator contract, not protection from a privileged service caller deliberately bypassing it via existing per-job queue RPCs or calling completion prematurely. No other optional consumer may run during rollout. Deployment composition must keep transport activation separate and ensure every automatic caller goes through this worker.

This patch does not claim scheduled sending, production activation, browser acceptance or final release readiness. Token/job/reservation retention, stuck-run operations, content/abuse review, full release regression and separately authorized rollout remain outstanding. Existing cadence reservations and provider evidence never authorize automatic resend.
