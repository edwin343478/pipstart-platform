# M21 approved optional-email retention: preview only

Owner-approved operating limits: valid unsubscribe tokens remain usable for the life of the account; completed content/provider evidence is retained for 90 days before compatibility-safe minimization; pending/preparing/sending/unresolved manual jobs are never automatically deleted; cadence reservations receive a 31-day window with active/review holds preserved; recovery audits receive 365 days with investigation holds preserved. Preferences and suppression records are outside this cleanup. These are the chosen application rules, not a claim about statutory retention requirements.

This batch installs only an owner-only inventory function and private investigation-hold table. No delete, redaction, cleanup executor, expiry, scheduler, API grant or automatic hold-release capability exists. `cleanupEnabled`, `automaticDeletion` and `resendAllowed` are always false. No queued content is changed, no budget reset, no worker unlocked and no email sent. Actual cleanup remains a later, separately reviewed/authorized implementation.

The aggregate report exposes policy version, evaluation time, status, approved durations and counts only. It returns no job/account identifiers, addresses, tokens, provider IDs, proof references or message content. It uses one stable statement snapshot and fixed elapsed-hour windows (2160/744/8760 hours), with strict older-than comparisons. Terminal age is measured from the latest queue creation/update, provider API acknowledgement, signed evidence receipt or individual event occurrence/receipt, so a newly received callback or future-dated event conservatively postpones review. Status other than accepted/suppressed never enters completed-content review.

Counts are review candidates, not approved deletions or projected storage savings. `terminalContentAction` is always `compatibility_review_required`: deleting terminal job rows would erase dedupe keys and cascade provider evidence, and changing prepared payloads can break callback digest verification. Before content minimization, design and test durable dedupe/tombstones, old-webhook handling and retained unsubscribe behavior. Until that compatibility work passes, even old terminal payloads stay untouched. Unsubscribe tokens currently have no expiry; this patch does not add one or silently prune apparently unused tokens.

The no-FK hold table supports a canonical job UUID or recovery run fingerprint plus an opaque `M21-` private proof reference. Holds never expire automatically, survive account/job deletion and are not proof of consent or executor shutdown. A job hold protects its content/reservation and any recovery audit containing that job. A recovery hold additionally protects every job/reservation named by the audit. The active admission's job IDs are protected even if a job row has disappeared; a non-idle/missing singleton reports `worker_review_required`, never permission for cleanup. Orphaned reservations older than 31 days can be counted for review if not otherwise held, but are not deleted here.

Recovery audit candidates must be older than 365 days, have no recovery/job hold or active-batch membership, and reference no extant unresolved job. Cadence candidates must be older than 31 days, not held/active, and not reference an extant unresolved job. Removing aged cadence entries later must never shorten the current 30-day partner, seven-day learning or daily budgets. Do not infer a fresh-send allowance or reconstruct a deleted job from an inventory count.

Only the database owner may inspect the function or manage holds through a separately authorized operator workflow. anon/authenticated/service_role receive neither execution nor table privileges; RLS has no policies. There is no browser/API hold-management route, no direct live-hold script and no migration backfill of hold records. An empty hold table means no hold has been recorded, not that no investigation exists: operators must record holds before approving future cleanup. Evidence/proof records remain private. Releasing a hold is a separate authorized decision and must not become an automatic cleanup side effect.

Generated tests cover owner isolation, approved durations, valid old tokens, old/recent terminal content, late provider events, unresolved states, 31/365-day review, direct/transitive holds, active admission and READ ONLY execution with unchanged rows. Application/hosted migration, live hold insertion, deletion, redaction and sending remain separate authorization gates. Retention execution, compatibility-safe payload minimization, content/abuse controls and final release regression remain outstanding.
