# M21 dormant Resend transport and signed delivery correlation

Prepared against `0eb6ecfe82950fa9fe3c193632f6a93b537d706f`. Additive only: existing queue, preference, unsubscribe, address-suppression, Auth SMTP, monitoring/sweep/watchdog and Skillcima code remain unchanged. No producer, enqueue/send route, worker, scheduler, campaign or environment-based send activation is added. Factory/consumer defaults keep optional delivery disabled. No real provider sends or app/hosted migrations occur in preparation.

## Immediate handoff and uncertain outcomes

`createOptionalResendTransport()` returns null unless explicitly passed enabled=true, a sending key and a receipt store. It does not read an environment variable or existing security/alert credentials. A future trusted worker must call the existing `processOptionalEmailJob` with this adapter, not call it directly or add another delayed queue behind its fresh authorization. The existing immutable SENDING marker and final fresh account/address/preferences check still precede the immediate HTTP handoff. Adapter validation occurs synchronously before fetch, with no database await before the request.

The adapter POSTs one recipient and precisely the durable subject/HTML/text/unsubscribe headers to the fixed Resend URL with the stable queue idempotency key. Sender is fixed to PipStart <no-reply@account.pipstart.net>. No CC/BCC, attachment, scheduled send, arbitrary header, override sender, SDK retry or redirect is allowed. Timeout is eight seconds, response JSON is bounded at 16 KiB. Every non-success, network/parse failure, lost receipt write or malformed acknowledgment is uncertain. No retry is performed, including 429; the existing consumer keeps a post-marker failure manual. HTTP acceptance is not delivery or inbox-placement proof. Provider idempotency is additional bounded protection, not an infinite retry guarantee.

## Correlation that does not authorize resending

Each send carries `pipstart_job_id` and `pipstart_payload_hash` tags. The digest is SHA-256 over an ordered sequence of UTF-8 byte-length-prefixed values: jobId, prepared recipient, subject, HTML, text, List-Unsubscribe and List-Unsubscribe-Post. This includes the immutable recipient and bearer-link payload without retaining a second copy in the new evidence tables. JS/PostgreSQL UTF-8 digest agreement is tested, including multibyte text. Job IDs/digests are linkable pseudonymous metadata, not anonymity or independent proof of the provider's full delivered MIME body. Provider account/API-key ownership remains a trusted boundary.

The new receipt table binds one job to one provider UUID and one prepared digest; the provider UUID is globally unique. API acknowledgment and signed callbacks can arrive in either order. An authentic callback can bind evidence for a SENDING/manual-uncertain job even if the HTTP response or final queue checkpoint was lost. No callback or receipt function changes job status, lease, attempts or prepared content. SENDING/manual jobs remain non-retryable. Never reset to pending, change the body/key or invent a new job to circumvent investigation.

The delivery-event ledger records independent facts, not a last-event-wins status. Duplicate event IDs are immutable no-ops; conflicting reuse, wrong recipient/digest/provider or provider reuse across jobs rolls back. Out-of-order sent/delivered/failure/complaint facts cannot erase one another. The summary RPC returns queue status, correlated provider ID, acknowledgment/signed-evidence flags and distinct event types, always `resendAllowed:false`. Absence of evidence is unknown, NOT proof that nothing was sent. There is no operator resend/unblock RPC in this patch.

## Separate signed endpoint

`/api/webhooks/resend/optional-delivery` has its own future `PIPSTART_OPTIONAL_DELIVERY_WEBHOOK_SECRET`. With no configuration it returns 503. Do not reuse or alter the working account-monitor/address-suppression endpoints or secrets. New webhook setup remains a separate authorized production configuration gate after schema deployment. Supported callbacks are sent, delivered, delivery_delayed, failed, bounced, complained and suppressed. Each request requires bounded UTF-8 JSON, valid Svix signature, exact PipStart sender, a single impacted recipient and both valid correlation tags. Untagged security mail, operators and other brands are ignored. Malformed correlated evidence is rejected, persistence/conflicts return retry_required for webhook redelivery, never permission to resend an email. No callback payload/body/subject/recipient is logged or retained by this endpoint. Deleted/unknown/never-prepared jobs are ignored, not resurrected.

The existing suppression endpoint independently handles address blocks; this correlation ledger does not create/remove blocks or weaken complaints. Existing account-email monitoring can observe the shared sender's failures without any code/config change here. Do not claim full monitoring integration or optional campaign readiness merely from a successful receipt.

## Storage and permissions

Two new RLS tables have no direct API grants, including service_role. Private digest/binding helpers are not API callable. Three empty-search-path owner-definer RPCs allow only service_role acknowledgment, authenticated event persistence and read-only per-job summary. Linked evidence cascades with queue/account deletion. Only job/provider/event IDs, digest, event type and timestamps are retained; original message/recipient/bearer URLs remain in the pre-existing sensitive queue. Retention, growth/access review and operational triage remain launch prerequisites; no automatic retention change or global provider reconciliation is introduced. Owner/service-key compromise is outside the claim of anonymous/learner isolation.

## Validation and remaining release gates

Unit tests use injected fetch and mocked stores only. The external tracked-source copy runs the full unit suite and lint/typecheck; the normal production build is included in the user-run apply/verification bundle. Generated SQL assertions run in a disposable local database with no real accounts/export. They cover early/out-of-order callbacks, API-first/event-first binding, digest/recipient/provider conflicts, deduplication, atomic receipt/event failure, manual-state preservation, account deletion and RPC/RLS isolation; separate connections test concurrent duplicate events.

Local and hosted application migration/acceptance require explicit authorization. Publishing and new webhook/secret configuration remain explicit gates, as do any controlled real provider send. Future real outbound acceptance must inspect recipient-delivered MIME/DKIM and one-click unsubscribe headers; JSON header presence is not sufficient DKIM certification. No optional worker/producer/campaign may be enabled before content/cadence caps, rate/abuse controls, operational unknown-send triage and end-to-end acceptance are reviewed. This patch does not create a UI, campaign, broad retry policy or production sending clearance.

Primary contracts verified against [Resend send API](https://resend.com/docs/api-reference/emails/send-email), [tags](https://resend.com/docs/dashboard/emails/tags) and [official outbound event schema](https://github.com/resend/resend-openapi/blob/main/resend.yaml). Outbound request tags are name/value arrays; callback tags are an object. Do not silently guess a changed callback format.
