# M21 private reviewed-content job producer

Five additions: a server-only catalog, one-job producer, two test files and this document. Existing queue, database, worker, transport, endpoints, preferences and suppression are unchanged. No migration, new HTTP endpoint, environment flag, audience enumeration, scheduled campaign, real queue insertion or send is supplied.

The production approved-content catalog is deliberately empty and frozen. This patch neither writes campaign copy nor grants human approval. Even explicitly calling the producer with enabled=true cannot enqueue with this version's real catalog. A later content addition requires a separately reviewed source patch and explicit human approval of its exact subject/HTML/text, category, revision, opaque approval reference and enqueue/scheduling window. No actual customer message is part of this batch.

Each record has id, revision, kind, subject, html, text, approvalRef, notBefore, notAfter and fingerprint. The checksum covers all nine other fields with UTF-8 byte-length-prefixed SHA-256, including review metadata/window. It detects drift, not malicious-owner changes or fabricated human approval. The catalog rejects malformed records or duplicate content IDs as a whole; lookup returns a frozen primitive snapshot. Source review/Git provenance and a protected private mapping of the opaque approval reference to the real human decision remain the authority. No database approval/audit ledger is added or claimed.

The private producer takes exactly one canonical account UUID, contentId, occurrenceKey and canonical UTC availableAt. It rejects email addresses, copy/category/preference overrides, extra keys and invalid timestamps. IDs/occurrences are strict lowercase ASCII identifiers. Default enabled=false returns before any lookup or SDK creation. The exact reviewed catalog entry is validated again before a queue adapter is constructed. The clock must be within its half-open review window and the requested availableAt must not be in the past or outside that same window. Both windows are checked before enqueue; metadata is not interpolated and no request data enters the approved subject/HTML/text.

Important time scope: this is an enqueue/scheduling approval window, not a guaranteed delivery deadline or automatic revocation. A queued job can be deferred by cadence, worker availability or outages beyond notAfter, and the accepted dispatcher does not reread this catalog at send time. Removing/expiring a catalog entry or disabling this producer stops future creation, not already persisted jobs or older deployments. Before future activation, approve the queued backlog/stop procedure explicitly; if a strict delivery-expiry/revocation requirement is adopted, it needs a separately reviewed durable send-time control. No such guarantee is inferred here.

Exactly one existing enqueue adapter call receives the account ID and a frozen copy of the reviewed content. The existing SQL still checks current account/category/frequency eligibility before a new job is inserted. Its account-scoped dedupe, concurrent insert protection and conflict handling remain authoritative; later send-time checks still enforce current suppression/address/preferences and cadence. Enqueue success is not delivery permission, a provider acknowledgement or inbox arrival.

The stable dedupe key hashes contentId plus occurrenceKey. It intentionally excludes revision, body, time and approval fingerprint. For the same account/content/logical occurrence, copy changes therefore encounter the existing SQL conflict instead of silently creating a replacement job; a schedule-only retry still honors the first schedule. Operators must preserve the original logical occurrence key, not invent a new one after a timeout. A genuinely different occurrence is a new reviewed scheduling decision, not a retry bypass. SHA-256 collision resistance is the boundary, not absolute equality proof.

Only validated aggregate queue outcomes and canonical job IDs are returned to the trusted server caller. Null/malformed acknowledgements or an enqueue exception return review_required without raw details, retries or an alternative key. A lost acknowledgement may follow a committed job: inspect the existing occurrence/job before considering any further action. Null/unconstructable adapter returns unavailable before enqueue. No token issuance, claim, worker admission, provider call or unlock/recovery is invoked by this producer.

This is a trusted server-side wrapper, not a database security boundary against a privileged service/owner client calling the existing RPC directly. There is no browser/admin enqueue UI, route, bulk producer, catalog mutation API or producer enable call site. The existing worker endpoint is independent and remains default-off. Country eligibility is not introduced.

Tests use generated review fixtures and mocked enqueue only; no fixture is added to the production catalog. They cover catalog closure/checksums/Unicode/canonical dates, strict input shape, empty-catalog no-write behavior, review/schedule boundaries, one exact reviewed payload, immutable logical occurrence keys, SQL suppression/duplicate/conflict outcomes, missing dependencies and sanitized uncertainty. Existing optional-email/unsubscribe tests, production no-emit overlay and new-file lint also run. Installing or publishing the five files creates no jobs and approves no content.
