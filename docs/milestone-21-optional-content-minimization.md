# M21 bounded owner-only optional content minimization

This dormant capability is separate from metadata cleanup and does not send email, activate a worker, schedule cleanup, remove accounts/jobs, or alter preferences/suppression. Installation does not minimize any existing content. Exactly three repository additions are supplied: migration, SQL acceptance and this document. Existing SQL functions are unchanged. The migration replaces exactly one prepared-payload CHECK and adds an AFTER insert/all-update guard so an accepted null payload requires private minimized facts and the exact terminal placeholders. Sending still always requires a prepared payload. The guard also rejects status-only reopening of a minimized job.

Eligibility is strictly older than 2160 elapsed hours (90 days) since the latest of queue creation/update, envelope-facts checkpoint, provider API/signed receipt or event occurrence/receipt time. Only accepted/suppressed jobs with complete matching content/envelope facts qualify. Direct job holds, recovery-run holds propagated to their jobs and active worker batches protect content. Pending/preparing/sending/manual uncertainty never qualifies. Missing/contradictory facts fail closed. New events, changed payload/state and selected-row holds invalidate the reviewed batch. The owner read-only plan exposes only aggregate count, plan timestamp/hash and fixed policy flags; its private candidate helper contains IDs/hashes, not an additional plaintext copy.

One owner-only invocation handles at most 100 jobs, ordered oldest first then UUID. It requires an exact plan no older than 15 minutes, no future timestamp, explicit stopped-senders attestation, and an opaque M21 proof reference. The singleton must be idle; a short table-lock window freezes queue/facts/holds/recovery/provider evidence for compare-and-update. Jobs are locked before facts. The batch is frozen once, never refilled or automatically drained. Lock timeout/deadlock/statement/audit failure aborts the transaction, including marker updates. The sender-stop assertion is a human operational attestation, not a technical remote-executor fence.

The executor sets the private minimized timestamp and replaces only subject, HTML, text and prepared payload with fixed placeholders/null, updating the queue change timestamp. It retains job/user IDs, original dedupe key/kind, schedule/status/attempts/provider ID and original content/envelope/recipient hashes. The private atomic receipt binds the exact reviewed plan, job count, operator database session and proof reference. Replay of the same fresh plan/proof returns the existing receipt and cannot process the next batch. Expired replays reject without changes. Empty plans create no receipt.

Valid unsubscribe tokens, account preferences, suppression, cadence budgets, recovery audits, holds, existing metadata-cleanup receipts, provider receipts and delivery events are not changed or deleted. Original body/key duplicate checks still work against the retained content digest. Accepted tombstones accept late correctly correlated signed/API evidence; wrong digest/provider/recipient remains rejected and accepted jobs remain terminal, not resendable. Suppressed jobs do not gain a new payload-free provider correlation exception. Provider/account systems and existing backups can retain their own copies; this is not secure erasure, anonymity or a data-subject deletion workflow. Digests and retained IDs remain linkable metadata.

All new functions/table are invoker/owner-only with no anon/authenticated/service_role grants, RLS and no policies. No public endpoint, automatic invocation, environment flag, cron, worker wiring or live-redaction execution helper is supplied. Owners can still change private rows directly; the guard is not tamper-proof against a database owner. The earlier generic retention inventory remains conservative and can count already minimized terminal rows; use the dedicated minimization plan for outstanding eligible content.

Before the first real execution, obtain separate batch-specific authorization, verify stopped executors and holds, retain a protected recoverable export/backup and private proof mapping, and decide access/retention for execution receipts. New receipts have no automatic pruning or account FK; the previous 365-day recovery-audit policy is not silently extended to them. Do not run an arbitrary fresh plan merely because the capability is installed. Migration and hosted acceptance are schema/preservation checks, not permission to redact live data.

Generated tests exercise exact 90-day/recent-provider boundaries, holds and uncertainty, 100-job cap without refill, wrong/stale/future plans, new evidence/holds and row drift, active admission, audit/update fault rollback, replay, original dedupe, late provider evidence, retained unsubscribe links and status/forged-tombstone guards. Two independent SQL connections prove one batch/one receipt. All generated database fixtures are removed afterward. Existing compatibility/cadence/worker/recovery/retention/metadata acceptance is rerun.
