# MP03 connected learner provider transport and UI

This patch connects the previously accepted learner intent to a server-only Auth provider adapter and an inline review/inspection panel in the approved People shell. Source preparation/apply does not activate any control, create an account, change a role, call a provider, install a migration or publish. The staff UI and provider adapter remain disabled unless their existing flags are exactly true, and the new dedicated server credential is configured. The private paused-Owner staff maintenance/recovery adapter remains a separate follow-up; this learner path cannot target current/former staff or legacy administrators.

## Authorization and transport

The browser verifies the current signed-in operator and capability before and after provider TOTP verification. It freezes the exact target, operation, absolute expiry, reason and request reference; stores the receipt only in component memory; and clears the entered code. The first verification obtains the accepted learner receipt only. An explicit second review confirmation invokes a Next server action. The server rechecks its configuration, verified user identity, strict access DTO and capability; its user-context RPC records the immutable intent and requests a one-use execution permit. Editable metadata and posted actors are not authority.

The authenticated claim rechecks the current receipt, actor/session/role/delegation, target class, exact command, verification/expiry and control version under the shared governance lock. It creates one durable delivery and a random one-use nonce, storing only its hash. The nonce alone cannot call Auth: service-only take/result RPCs additionally require the separate server credential. Conversely, a service credential alone cannot issue user claims or inspect raw journal/permit tables. The public claim endpoint may be called directly by an already authorized operator, so all authorization is in SQL; the server action/UI is not the security boundary.

The server takes the permit once before calling the existing bounded provider adapter. Take rechecks live provider session/factor/ban/deletion and delegation, control version and target eligibility. Concurrent takes have one executable winner. A consumed or lost permit never authorizes another update. Results require that exact consumed dispatch permit, preserve known acknowledgment versus uncertainty and append immutable events atomically. Permits bind mode: an inspection permit cannot append a successful update result. Event records retain the verified authorizing actor reference and permit correlation, while trusted paused reviews retain explicit operator provenance rather than inventing an authenticated person.

The dedicated environment variable is `PIPSTART_M22_ACCOUNT_PROVIDER_SECRET_KEY`. It is server-only, never falls back to `SUPABASE_SECRET_KEY` and is never sent through page props. No key or flag is created/changed by this patch. Supabase secret keys retain powerful project capabilities; dedicating/naming the credential improves separation and revocation, but does not make the underlying Auth administration API a narrowly scoped credential. RPC grants restrict the journal transport. Secret custody, correct project binding and explicit rollout approval remain necessary. No extra database password or broad private-schema/API grant is introduced.

Each provider fetch has a seven-second abort budget and the accepted adapter has bounded awaits with no automatic update/claim/result retry. An aborted or timed-out request may still have taken effect remotely. Known provider acknowledgment is distinct from an independently observed current state. The UI never interprets a request row or an absent response as proof that the provider changed or cannot still finish.

## Races and stop/recovery

An unresolved `prepared`, `dispatched` or `unknown` delivery blocks another delivery for that learner even after the original five-minute receipt expires. Staff membership and legacy-admin promotion are fenced while such a learner delivery exists, including the interval after a take commits and before the remote update finishes. Re-enabling paused staff control also refuses unresolved deliveries. Dispatch does not hold a database transaction open during network I/O.

Pause/revocation before take prevents provider execution; pause/revocation after take cannot cancel already authorized/in-flight remote work. Exact outcome recording remains possible after a stop. A trusted database operator, while paused, can cancel a still-prepared delivery or record an explicit observed outcome for an unknown delivery using the exact request/dispatch. Cancel and take serialize: cancellation cannot undo a dispatched operation. An observation is not causality or proof an in-flight request has finished; the operator must review outstanding work/provider evidence before recording a resolution or re-enabling staff. These private review primitives grant no public/service API execution and no permission for the agent to perform a real review action.

## Product behavior and privacy

The existing People design, inline panel, native labels, authenticator selector, focus/status pattern and responsive styles are reused. The learner account button appears only for an eligible-looking nonstaff row when the server configuration and learner-management capability are available. SQL still decides eligibility, including legacy profile flags and former staff. A delegated Administrator does not gain role-management controls.

The operator chooses suspend/reactivate, the exact end time in device-local time and a fixed reason. A fresh code leads to an explicit exact-command review. Confirmation can send one update. Busy-state/ref guards block double clicks, and uncertainty blocks another action in that panel. Request references survive in the panel for copying by the user; codes/tokens/nonces are not placed in URLs, browser persistence, rendered markup or logs. An existing reference can be checked after reload by the original currently authorized actor or Owner, with target matching to the selected person.

Suspension prevents new logins according to the provider ban duration. Existing learner access tokens/sessions may remain usable until expiry/sign-out; this patch does not promise instant global session revocation. Reactivation does not restore staff grants. Current/former staff Auth operations remain on the separate Owner-only path.

Inspection requires a new fresh verification, can only call `getUserById`, returns a minimized desired/other/unavailable observation and never updates the account or resolves the journal. It cannot be used as an update retry. The panel distinguishes provider acknowledgment, durable delivery state and observation. Emails, metadata, factors and full provider JSON are not fetched for the People list or returned by the server action.
