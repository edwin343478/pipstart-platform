# M21 optional-email cadence reservations (dormant)

Owner-approved limits: learning All = at most one/24 hours and three/168 hours; Weekly = one/168 hours; partner offers = one/720 hours; every optional category combined = one/recipient/24 hours; platform = 50 optional handoff reservations/24 hours. These are rolling elapsed durations, not calendar resets or provider-plan promises. Security/reset/operator emails do not use this queue or budget.

This focused patch changes only the existing begin RPC and adds its private reservation ledger. No worker, producer, send route, schedule, key, enable switch or provider request is introduced. The later worker must still enforce one worker and at most five jobs/run. Those run controls are NOT claimed implemented here.

The same SECURITY DEFINER/empty-search-path/service-only boolean RPC now serializes handoff budgeting under a global transaction advisory lock, then locks/checks the claimed job and lease. Existing prepared-envelope checks stay intact, with the same canonical ASCII address hash as address suppression. It reserves the budget atomically with the SENDING marker. Any database failure rolls back both. All callers of the existing RPC, including older consumers, are capped; there is no uncapped alternate handoff RPC. The sender still runs its final fresh eligibility/address read after begin and invokes its provider immediately without another database await.

Reservations count possible handoffs, not delivered messages. Sending/manual-uncertain/accepted attempts all consume capacity. No outcome automatically refunds a reservation, including a crash or opt-out observed after the marker. This is deliberately conservative and can defer mail that was never sent. False-positive suppression is preferred to duplicate/over-cap sends. Unknown evidence is never permission to resend.

All learning kinds count toward either learning mode, so switching All/Weekly cannot reset the window. All optional categories share the daily recipient cap. Address hashing lowercases the validated unquoted ASCII mailbox; it does not collapse Gmail dots/plus aliases or establish a global anti-Sybil guarantee. Concurrent jobs cannot both consume the last platform/address slot. Global serialization is suitable for the initial 50/day ceiling, not a claim of high-throughput scalability.

When a cap blocks a proven pre-handoff attempt, begin returns false after clearing the preparation lease and deferring the existing job to the earliest time every current cap can permit it. No envelope or reservation is committed for that denial. The preparation-attempt increment is refunded only for this proven no-handoff deferral; `available_at` prevents immediate reclaim. The reason is `cadence_limited`. The unchanged consumer reports `lease_lost` and performs no transport/finish/release. A future worker must regard this as no handoff and respect the database due time, never create a replacement job to evade a cap. There is no automatic retry of SENDING/manual/provider outcomes.

The pre-existing envelope builder issues unsubscribe tokens before begin, so a deferred attempt can leave unused token records for that learner. This gate does not remove/reuse those tokens or pretend to solve token growth. Due-time enforcement bounds cadence retries; retention and producer/worker abuse controls remain necessary before launch.

The ledger stores only job UUID, canonical-address hash, kind and reservation time: no plaintext address, message, key or bearer link. RLS is enabled with no policies and no direct API grants, including service_role. The ledger intentionally has no account/job FK and survives deletion, preventing recreation from resetting address or global caps. This differs from the account-linked message/receipt/event tables. Hashes remain pseudonymous personal metadata, not anonymity. A bounded retention/pruning policy and access review remain launch prerequisites; no pruning or budget-reset API is added. Existing Auth, preferences, suppression/import ledgers, security monitoring and Skillcima are unchanged.

Migration locks the jobs table while installing the gate. Existing rows with any prepared handoff are conservatively seeded using the latest known job checkpoint time (not an invented provider-send time). Unsupported prepared recipients abort the migration for review rather than silently escaping the cap. The migration does not edit existing queue rows or claim historical sends that have already been deleted. Keep optional producers/workers disabled during rollout and backfill review; do not treat this as hot migration clearance or reconstruct deleted history from guesses.

Generated disposable-database tests cover backfill, safe cap deferral, exact rolling boundaries, mixed learning kinds, setting changes, partner and platform limits, retained unknown reservations, account recreation, malformed bodies, atomic rollback and API isolation. Separate-connection tests check contending claims for the last slot. No real emails or local/hosted application migrations run during preparation. Local/hosted migration acceptance and publishing remain explicit subsequent gates.
